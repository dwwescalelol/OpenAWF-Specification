# OpenAWF Specification 0.1.0

Status: draft. Breaking changes are expected before 1.0.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

This document is normative. The JSON Schema in `schemas/0.1.0/` validates structure only. Where the two conflict, this document wins.

## 1. Terms

- **Workflow.** A document describing an agentic process as a finite-state machine of tasks.
- **Finite-state machine.** A set of states and the transitions between them. Each state of a workflow is a task. The flow starts at one task and moves along transitions until it reaches a terminal task.
- **Task.** One unit of work for an agent: a prompt, the data it takes and returns, and the tools it may use.
- **Transition.** The rule for where the flow goes after a task finishes.
- **Outcome.** A named result a task reports when it finishes, such as `pass` or `fail`. A task with outcomes branches on them.
- **Terminal task.** A task whose transition is `null`. The flow ends after it.
- **Draft.** A document whose `sha` is `null` or absent. A draft MAY change.
- **Sealed document.** A document whose `sha` holds the hash of its content. A sealed document MUST NOT change.
- **sha.** The content hash of a document, prefixed with its algorithm, such as `sha256-<hex>`.
- **Runner.** A program that executes a workflow.
- **Tool.** An operation an agent calls, provided by an MCP server.
- **Artifact.** External state a task creates or changes through a tool, such as a commit, a pull request comment, a ticket or a file.

## 2. Documents

A workflow document is a YAML or JSON object. YAML documents MUST be valid under the YAML 1.2 core schema. A tool MUST reject duplicate keys and MUST expand aliases before processing. A task document is a Markdown file with YAML frontmatter (section 4.2).

Every key this specification defines is lowercase. A key of more than one word joins its words with hyphens (kebab-case), such as `external-version`.

### 2.1 Workflow fields

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `openawf` | yes | string | The spec version the document is written against. MUST be `0.1.0`. |
| `name` | yes | string | The workflow's name. |
| `summary` | no | string | One line on what the workflow does. |
| `model` | no | string or list of strings | The model every task uses unless the task overrides it (section 2.4). |
| `metadata` | no | object | Free keys describing the workflow (section 2.3). |
| `license` | no | string | The workflow's license, as an SPDX license identifier such as `Apache-2.0`. |
| `version` | no | string | The workflow's version, `major.minor.patch`. Required to seal. |
| `sha` | no | string or null | The content hash. `null` in a draft. |
| `external-version` | no | string | A version identifier assigned by an external tool, such as an n8n `versionId`. |
| `source` | no | string | Where the workflow was fetched from. Omitted when it is authored in place. |
| `start` | yes | string | The name of the task the flow begins at. |
| `orchestration` | yes | object | Transitions, keyed by task name (section 3). |
| `tasks` | yes | object | Tasks, keyed by name (section 4). |
| `mcp` | no | object | MCP servers, keyed by name (section 6). |

A document MUST NOT contain fields this specification does not define, except extension keys (section 2.2).

### 2.2 Extensions

An extension key is a member of the workflow object, a task or an edge object whose name starts with `x-`. The workflow object, a task and an edge object MAY carry extension keys. An extension key SHOULD name the runner that reads it, such as `x-claude`, and hold an object of that runner's settings.

A runner MUST ignore extension keys it does not understand. A tool that bundles or seals a document MUST keep its extension keys. Extension keys are part of the hashed content (section 8.2).

### 2.3 Metadata

`metadata` is an object of free keys that describe a workflow or a task. Runners do not use it to execute. These keys have a defined meaning:

| Key | Type | Meaning |
| --- | --- | --- |
| `tags` | list of strings | Labels for search and grouping. |
| `authors` | list of strings | The people or organisations who wrote the document. |
| `icon` | string | A URL or relative path to an image that represents the document. |

Any other key is allowed. `metadata` is part of the hashed content (section 8.2).

### 2.4 Models

A model is written `provider/name`, such as `anthropic/claude-sonnet-5`. The provider is the text before the first `/`. The name is the rest and MAY contain `/`. A tool that converts a model MUST split it on the first `/` only.

`model` is one model, or a non-empty list of distinct models. A list is an ordered fallback chain: a runner uses the first model in the list it can run.

Endpoints, credentials and API settings belong to the runner and go in extension keys (section 2.2).

## 3. Orchestration

Each key of `orchestration` names a task. Its value is the transition out of that task, in one of three forms:

- `null`: the task is terminal.
- An edge: an unconditional transition to one task.
- A branch: an object mapping each outcome to an edge.

An edge is a task name, or an object:

| Field | Required | Meaning |
| --- | --- | --- |
| `task` | yes | The task the edge leads to. |
| `retries` | no | Attempts after the first failure before the task fails hard. `null`, the default, retries without limit. `0` allows one attempt. |
| `session` | no | `fresh`, the default, starts the task in a new agent session. `resume` continues the session of the task the edge came from. |

A branch MUST NOT use `task` as an outcome name, because `task` marks an edge object.

## 4. Tasks

### 4.1 Task fields

A task entry is an inline task or a reference (section 5).

| Field | Required | Meaning |
| --- | --- | --- |
| `body` | yes | The request for this step, in Markdown, written for any agent. |
| `system` | no | Standing instructions for the agent, in Markdown. |
| `summary` | no | One line on what the task does. |
| `outcomes` | no | The outcomes the task may report. Each name is unique. |
| `input` | no | A JSON Schema the data passed to the task MUST satisfy. |
| `output` | no | A JSON Schema the task's result MUST satisfy. |
| `model` | no | Overrides the workflow's `model` (section 2.4). |
| `metadata` | no | Free keys describing the task (section 2.3). |
| `license` | no | The task's license, as an SPDX license identifier such as `Apache-2.0`. |
| `uses` | no | Names of servers in `mcp` the task requires. |
| `version` | no | The task's version, `major.minor.patch`. |
| `sha` | no | The task's content hash. |
| `external-version` | no | A version identifier assigned by an external tool. |
| `source` | no | Where the task was fetched from. A bundled reference records itself here. |

`system` holds the instructions that hold for the whole task, such as the agent's role and rules. `body` holds what the task asks the agent to do. A runner SHOULD pass `system` as the system prompt and `body` as the first user message. A tool that converts a task to a format with a single prompt field MUST write `body` alone when `system` is absent. When `system` is present, it MUST write `system` with trailing line breaks removed, then two line breaks, then `body`.

### 4.2 Task documents

A task document is a Markdown file. It opens with YAML frontmatter between `---` lines. The frontmatter holds every task field except `body`, plus `openawf` and any extension keys. The Markdown after the frontmatter is the body. The frontmatter MUST NOT contain `body`.

## 5. References

A task entry of the form `{ "$ref": <string> }` points at a task document. A reference is one of:

- A path. A relative path resolves against the directory that holds the tool's store, or the workflow's own directory when there is no store.
- An id pinned to a version: `[<namespace>#]<id>@<version>`. This version does not define how a namespace resolves to a location. A tool that supports pinned ids defines its own resolution.

Bundling replaces each reference with the task it points at and records the reference in the task's `source`. Orchestration keys and edges name tasks by their key in `tasks`, never by reference.

A sealed workflow MUST NOT contain references.

## 6. MCP servers

`mcp` declares the MCP servers a workflow depends on. It states the requirement only. Connection details (command, URL, credentials) are resolved by the runner and are not part of the document.

| Field | Meaning |
| --- | --- |
| `transport` | `stdio`, `http` or `sse`. A hint for the runner. MCP has deprecated `sse` in favour of Streamable HTTP. |
| `tools` | The tools the workflow uses from the server: a list of names, or `"*"` for all. Defaults to `"*"`. |

A runner SHOULD expose to each task only the tools of the servers it names in `uses`.

Server sources, tool-contract hashes and secrets are under revision for a later version.

## 7. Validation

A conformant validator runs three passes in order: structure against the JSON Schema, then the graph, then the hash. It MUST report every error below and MUST NOT accept a document with an error.

### 7.1 Errors

- `start` does not name a task in `tasks`.
- An edge names a task not in `tasks`.
- A task has no orchestration key, or an orchestration key names no task.
- A task with `outcomes` has a plain edge or `null` instead of a branch.
- A branch names an outcome the task does not declare.
- A branch has no edge for one of the task's outcomes.
- A branch is given for a task with no `outcomes`.
- No task is terminal.
- A task reachable from `start` has no path to a terminal task.
- A name in `uses` is not a server in `mcp`.
- A non-null `sha` does not match the document's content (section 8).
- A reference does not resolve, or its target does not validate.

### 7.2 Warnings

- A task is not reachable from `start`.

A validator MAY offer a mode that treats warnings as errors.

## 8. Sealing

Sealing fixes a document's content and gives it an identity.

### 8.1 Procedure

To seal a workflow, a tool MUST:

1. Require a `version`.
2. Require every referenced task to be sealed.
3. Bundle the document (section 5).
4. Compute the sha (section 8.2) and write it to `sha`.

### 8.2 Hash

The sha is computed over a canonical form:

1. Take the bundled document as a JSON value.
2. Omit optional members this specification defines when they are null, empty strings, empty arrays or empty objects. Values inside `input` and `output` are JSON Schemas and are kept exactly as written. Values inside `metadata` and values of extension keys are kept exactly as written, including null and empty values. An empty `metadata` object is itself omitted.
3. Write an edge with no `retries`, no `session` and no extension keys as its task name string.
4. Remove the top-level `sha` and `version`. The `sha` and `version` of inline tasks stay in the hashed content.
5. Serialize with the JSON Canonicalization Scheme, RFC 8785.
6. Hash the bytes with SHA-256 and write `sha256-` followed by the lowercase hex digest.

Defaults are not filled in or removed. An edge with `session: fresh` and an edge with no `session` mean the same thing but hash differently, as do `tools: "*"` and an omitted `tools`. Authors who need equal shas write equal documents.

A task document hashes the same way, with its frontmatter and body as one object. An inline task's `sha` is the hash of that task as a task document carrying the workflow's `openawf`, with `source` removed when the task was bundled.

Validators MUST accept `sha256-`, `sha384-` and `sha512-` prefixes and MUST recompute the hash with the named algorithm.

### 8.3 Identity

The version is a label and is excluded from the hash. `external-version` records an identifier from another tool. It does not replace `version` or `sha`, and it is part of the hashed content. Two versions with identical content share a sha. A document with `sha: null` has no identity.

## 9. Versioning

Versions are `major.minor.patch`. A workflow pins each referenced task to an exact version. There are no version ranges. A sealed version never changes. A change is a new draft sealed at a newer version.

## 10. Execution

This version does not define execution. A runner that executes a 0.1.0 workflow SHOULD start at `start`, follow transitions as section 3 defines, and stop after a terminal task. The following are not yet specified and are planned for a later version:

- How a task's result becomes the next task's input.
- How a task reports its outcome.
- What counts as a failure for `retries`.
- When a runner moves to the next model in a fallback list.
- What context a resumed session carries.
- How tools from `uses` are bound to the agent.
- How a runner stamps artifacts with the workflow's identity.

## 11. Conformance

- A conformant validator implements section 7.
- A conformant sealer implements section 8. Two conformant sealers MUST produce the same sha for the same document.
- This version defines no runner conformance class.
